# SILT

Source: `extern/silt`, https://github.com/ByteHamster/silt, branch `build-fix` at commit `55ee50b`
(2022-03-22). This is upstream SILT (https://github.com/silt/silt, last commit 2015) plus build fixes
by the PaCHash author, the version used in the PaCHash paper's experiments:
`tbb::atomic` → `std::atomic` (removed in current oneTBB), OpenSSL 1.1+ API, C++11 fixes, and
`Open()` no longer deletes the database. The algorithms are unchanged. Upstream does not build with
current TBB/OpenSSL. Shared behaviour (same data as BOA, results format, measurement notes):
[../README.md](../README.md).

| `--mode` | SILT structure | Compare with BOA's |
|---|---|---|
| `combi` (default) | combined store: log store → hash stores → sorted store, with background conversion and merges | online mode, interleaved |
| `sorted` | sorted store alone, bulk-built (SILT's sorter, then the sorted store); static, `--interleaved` rejected | online-suspended mode (`--suspended` / `--materialization`) |

## Build

```bash
sudo apt-get install libxerces-c-dev libssl-dev libgsl-dev libtbb-dev libboost-dev
experiments/competitors/silt/build.sh        # → build-competitors/silt/silt_bench
```

SILT's own build is autotools. Its `configure` script requires gtest and Boost.Thread just to run, and
turns Berkeley DB and nsort support on or off depending on what is installed. Instead, `CMakeLists.txt`
compiles SILT's library sources directly (as PaCHash-Experiments does), with a fixed `config.h`, so every
machine builds the same:

| Build setting | Value | Why |
|---|---|---|
| `CMAKE_BUILD_TYPE` | `Release` | |
| `HAVE_LIBDB` | not defined | no Berkeley DB store (not used by the combined or sorted store) |
| `HAVE_LIBNSORT` | not defined | SILT's own sorter instead of the commercial nsort library |
| Sources left out | `fawnds_bench.cc`, `cindex/bench_SOSP.cpp` (programs with `main`), `bdb.cc` (Berkeley DB), `fawnds_sf_ordered_binarysearch.cc` (unused alternative sorted store, as in PaCHash-Experiments), `utils/*.c` (debug/timing helpers needing a header generated by autotools; not used by the stores) | |
| Warnings | `-w` for SILT's sources only | 2011-era code |
| C++ standard | 17 | as in PaCHash-Experiments |

## Run

```bash
build-competitors/silt/silt_bench --size 10000000 --key-dist uniform --query-dist all
build-competitors/silt/silt_bench --mode sorted --size 10000000 --query-dist all
experiments/competitors/silt/run.sh                      # combined store; SILT_ARGS="--mode sorted" for the sorted store
```

`silt_bench --help` lists all options.

## Every SILT setting

SILT is configured through XML. The driver starts from `silt_combi.xml` or `silt_sorted.xml` in this
folder. Their values are SILT's own, from `test/fawnds/testConfigs/testCombi.xml` (cuckoo
`hash-table-size` 131072, `keys-per-block` 1, `bucket-size` 128, `skip-bits` 0). The driver fills in the
empty values and **writes the final XML into every results file** (between `SILT configuration begin` and
`SILT configuration end`).

| Option | Meaning | Default |
|---|---|---|
| `--mode combi\|sorted` | see above | `combi` |
| `--buffered-io` | `use-buffered-io-only` = 1 for every hash table and data store | 0 (SILT's default: direct I/O for random reads) |
| `--db-dir PATH` | directory for SILT's files (and its sorter's / merges' temporary files), removed before and after each experiment unless `--keep-db` | `silt_bench_db` |

Filled in by the driver:

| Setting | Value |
|---|---|
| `key-len` | 8: keys are the 8-byte `MurmurHash64` of the `uint32_t` key, the same function as BOA's `HashFunction`. SILT expects uniformly distributed fixed-length keys (its cuckoo tables and trie index use key bits directly; the SILT paper uses SHA-1 keys) |
| `data-len` | 1 (value `'a'`, like BOA's `char` value) |
| `size` | `--size` (SILT needs the number of keys up front) |
| `temp-file` | `--db-dir` |
| file paths | inside `--db-dir` |
| combined store | `Flush()` after the last insertion (part of the insertion time) |
| sorted store | keys go to SILT's sorter (`type sorter`, same key/data length, `size`, `temp-file`); after the last insertion the sorter is flushed and enumerated into the sorted store, which is then flushed. All of it is part of the insertion time, like `boa`'s consolidation in suspended mode |

## Results file

Name: `silt_<mode>_<direct|buffered>_<key dist>_<query dists>_exp_<N>.txt`
(interleaved: `silt_interleaved_combi_<direct|buffered>_<ins>_<queries>_exp_<N>.txt`), in the current
directory, or `--log-file`.

SILT-specific lines: the final XML configuration, `disk bytes` (size of SILT's files) at each insertion
checkpoint and batch, and `SILT disk bytes` at the end. SILT also prints its own per-stage latency
statistics to stdout when it shuts down; those are not in the results file.

## Notes

- SILT's in-memory index sizes follow from its design and the XML values (hash table sizes, trie
  parameters). There is no single memory-budget option; compare memory with `Peak RSS bytes`.
- Even with direct I/O, SILT reads through the page cache for chunks it has written but not yet synced,
  and it keeps a small internal page cache (`file_store.cc`). In small tests, queries on the sorted store
  read nothing from the device (`OS bytes read 0`). Use data sets larger than RAM, or the memory limit in
  `run.sh`, as for every page-cache-backed competitor.
- The combined store converts and merges stores in background threads.
